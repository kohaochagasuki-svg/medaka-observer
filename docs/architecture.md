# 設計メモ

## 現在の動画処理

- HTMLVideoElementを1個使用し、`preload="metadata"` で最初にメタデータを取得する。
- Fileをblob URLで参照する。FileReaderや`file.arrayBuffer()`による動画全体のコピーは行わない。
- 再生に必要な読み出し・デコードはブラウザに任せる。フレームをJavaScriptに取り込まない。
- 差し替え・ページ終了時は一時停止、src除去、load、revokeObjectURLの順で参照を解放する。BFCacheに入る場合はURLを維持する。
- バックグラウンドに移ったら再生を停止する。
- 映像の幅・高さからobject-fit: containの実表示領域を計算し、その領域内で中央線の位置を0〜100%で保持する。回転・リサイズ時に再計算する。
- CSPの`connect-src 'none'`、`media-src blob:`で動画や条件の外部送信経路を制限する。本番は同一配信元のHTML・CSS・JS・SVGだけで構成する。
- デコード用メモリやブラウザのキャッシュ上限はWebアプリから厳密には制御できない。4K、高ビットレート、対応外コーデックは負荷や再生失敗の原因になる。30分動画での実機性能は未検証。

## 将来の自動解析（設計のみ・未実装）

1. 再生用と解析用の動作を分離し、動画のメディア時刻を基準に少しずつフレームを取り出す。
2. 解析解像度を例として長辺640px程度に縮小し、対象の泳速に合わせてサンプリング頻度を決める。速い横断を取り逃す可能性があるので、実験動画で評価して決定する。
3. 小さなCanvas／OffscreenCanvasとWeb Workerを使う。Worker処理の完了をawaitしてから次のフレームを送る。処理待ちキューは1枚、デコード済みフレームも最小限に制限し、ImageBitmap／VideoFrameは使用直後にcloseする。
4. 保持するのは直前の追跡位置と横断イベント（時刻、個体ID、方向、信頼度）のみとし、画像配列を蓄積しない。長いイベント記録にはIndexedDBを検討する。
5. 中央線の両側に小さな判定帯を設け、線付近の揺れを複数回の横断と数えない。複数個体、遮蔽、反射、背景変化の精度を検証する。
6. 進捗は「処理済みの動画時刻 / 対象動画時間 × 100」で表示する。解析成功と中止を区別し、中止した結果を完了として表示しない。
7. 中止ボタンはAbortControllerで通知し、各シーク・フレーム取得・Worker応答の待機でも中止を扱う。待機中のPromiseを解決・破棄し、Worker終了、フレームclose、Canvas解放を行う。世代IDで過去の処理応答が画面を更新することを防ぐ。
8. 確認・修正後のイベントだけをCSV出力対象にする。解析の設定と観察条件も残し、再現性を保つ。

これらの処理、進捗表示、中止ボタンは今回のコードには追加していない。
